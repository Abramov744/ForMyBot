# ForMyBot — funding-бот с веб-калькулятором и алертами

Стратегия: заработок на funding с шорта на фьючерсах, хедж — лонг той же
монеты на споте. Бот собирает funding fee с Aster / Bybit / Lighter / MEXC /
Gate, шлёт ежедневный отчёт и отвечает на команды в Telegram, считает
чистую доходность сделок через веб-калькулятор и алертит, когда прогнозный
funding по открытой позиции уходит в минус.

## Компоненты

- `funding_report.py` — вся логика работы с API бирж (история funding,
  список открытых позиций) + сборка текстовых отчётов. Используется всеми
  остальными файлами. Сюда же вынесен общий короткоживущий (по умолчанию 15
  сек, `POSITIONS_CACHE_TTL_S`) кэш сырого ответа биржи со списком позиций
  (`_cached_raw_positions` + `_*_positions_raw` по каждой бирже) — раньше
  funding_report/`liquidation_alerts.py`/`short_position_tracker.py`
  независимо делали свой отдельный HTTP-запрос к одному и тому же
  приватному эндпоинту позиций с одинаковыми параметрами (например
  `GET /v5/position/list` у Bybit — до трёх идентичных запросов в трёх
  файлах), просто разбирая из ответа разные поля под свою задачу. Заметнее
  всего было при старте процесса (все фоновые циклы стартуют почти
  одновременно и у каждого первая проверка выполняется сразу) и в команде
  `/rates`, которая дёргает список позиций и цены входа/текущую для одной и
  той же биржи дважды подряд в рамках одного вызова.
- `bot_poll.py` — обработчик команд `/report`, `/calendar`, `/positions`, `/rates`, `/balance`.
- `bot_worker.py` — постоянный Telegram-бот (long polling).
- `funding_chart.py` — графики для Telegram: годовая ставка (APR) по
  открытым позициям (кнопка «📈 Открытые позиции») и прибыль по дням/
  накопительным итогом за период (кнопка «📅 Календарь», см. раздел ниже).
- `funding_alerts.py` — почасовая проверка прогнозного funding по открытым
  позициям, алерт в Telegram при уходе ставки в минус.
- `liquidation_alerts.py` — проверка риска ликвидации по открытым позициям,
  алерт в Telegram, когда цена проходит 70% (настраивается) пути от входа
  до ликвидации — см. раздел ниже.
- `calculator.py` — расчёт чистой доходности сделки (funding − комиссии
  открытия + спред спот/фьючерс на входе) за период/биржу/монету, для всех
  шести подключённых бирж, включая KuCoin.
- `entry_price.py` — авто-подбор цен открытия для калькулятора: цена шорта
  берётся из данных открытой позиции на фьючерсной бирже, цена споta — из
  истории сделок на подключённых спот-биржах (Bybit/KuCoin/MEXC/Gate) и,
  если задан `UNISWAP_WALLET_ADDRESS`, из истории переводов кошелька на
  Uniswap — сразу на всех EVM-сетях, которые поддерживает Etherscan (см.
  ниже). Если не нашлось — поле остаётся пустым для ручного ввода.
- `balances.py` — сводный баланс по всем биржам (включая KuCoin) + Aave v3
  (on-chain), суммарно в USD. Веб-страница `/balances` и команда `/balance`
  в Telegram. Rabby wallet и Fluid сознательно не мониторятся — см. раздел
  ниже.
- `app.py` — **точка входа для деплоя**: веб-страница калькулятора (Flask,
  под Basic Auth) + фоново bot_worker + фоново funding_alerts + опционально
  фоново sheets_sync + опционально фоново short_position_tracker, всё в
  одном процессе/сервисе.
- `sheets_sync.py` — периодически (по умолчанию раз в час) пишет суммарный
  funding по открытым сейчас позициям в столбец P Google Sheet взамен
  ручного ввода (см. раздел ниже). Работает только если заданы
  `GOOGLE_SHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON` — иначе просто выключен.
- `short_position_tracker.py` — почасово ищет НОВЫЕ открытые шорт-позиции
  сразу по всем 6 биржам (Aster/Bybit/KuCoin/Lighter/MEXC/Gate) и, если на
  споте нашлась встречная покупка того же объёма, сам создаёт новую строку
  в таблице (монета в B, время открытия в D, биржа в O) — см. раздел ниже.
  Тоже работает только при заданных `GOOGLE_SHEET_ID`/
  `GOOGLE_SERVICE_ACCOUNT_JSON`.
- `aster_interval_history.py` — фоново (побочным эффектом цикла
  `funding_alerts`) копит в отдельной вкладке Google Sheet историю
  ФАКТИЧЕСКИ действовавшего интервала начисления funding по символам на
  Aster (он иногда временно сокращается биржей при волатильности) — нужно
  графику APR, см. раздел ниже. Тоже требует `GOOGLE_SHEET_ID`/
  `GOOGLE_SERVICE_ACCOUNT_JSON`.
- `kucoin_symbol_history.py` — фоново (побочным эффектом часовой
  синхронизации `sheets_sync.py`) копит в отдельной вкладке Google Sheet
  реестр всех когда-либо виденных открытыми символов KuCoin — нужен
  `/report`/`/calendar`, см. раздел «KuCoin в funding-контуре» ниже про то,
  зачем. Тоже требует `GOOGLE_SHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON`.
- `.github/workflows/` — вспомогательные ручные workflow'ы (Claude Code
  Action, ручной запуск `/report` через `bot_poll.py` при необходимости);
  ежедневная автоматическая рассылка отчёта по расписанию убрана — тот же
  отчёт доступен в любой момент по команде `/report` в самом боте.

## Деплой на Railway

`Procfile` содержит `web: python app.py` — Railway поднимет один сервис,
который одновременно: слушает HTTP на `$PORT` (калькулятор) и в фоне гоняет
Telegram-бота и алерты.

### Переменные окружения

Обязательные (как и раньше):

- `ASTER_USER_ADDRESS`, `ASTER_SIGNER_ADDRESS`, `ASTER_SIGNER_PRIVATE_KEY`
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — второе можно указать как ОДИН
  chat_id (как раньше) или НЕСКОЛЬКО через запятую (`123456,789012`), чтобы
  ботом мог пользоваться не только владелец, но и ещё один Telegram-
  аккаунт — тот же бот, те же биржевые ключи и та же Google-таблица, без
  второго деплоя. Оба аккаунта одинаково могут писать команды и получать
  ответы, и оба получают фоновые алерты/рассылки (funding-алерты,
  закрытие позиций и т.п.) — они уходят на все перечисленные chat_id
  сразу. Узнать chat_id второго аккаунта — написать боту
  [@userinfobot](https://t.me/userinfobot) от его имени, он пришлёт id в
  ответ.

Опциональные (биржа участвует в отчётах/калькуляторе/алертах, только если
её пара задана):

- `BYBIT_API_KEY` / `BYBIT_API_SECRET` (+ опционально `BYBIT_PROXY`)
- `LIGHTER_ACCOUNT_INDEX` / `LIGHTER_AUTH_TOKEN`
- `MEXC_API_KEY` / `MEXC_API_SECRET` (+ опционально `MEXC_PROXY`)
- `GATE_API_KEY` / `GATE_API_SECRET` (+ опционально `GATE_PROXY`)
- `DYDX_ADDRESS` (+ опционально `DYDX_SUBACCOUNT_NUMBER`, по умолчанию
  `"0"`; `DYDX_PROXY`) — dYdX v4 некастодиальная, никакого API-ключа не
  нужно, только адрес кошелька (позиции и баланс читаются публично через
  Indexer API). Полностью интегрирован во все те же механизмы, что и
  остальные пять бирж (автозапись новых шортов, margin/ликвидационные
  алерты, детекция закрытия, `/rates`, столбец P, `/report`/`/calendar`/
  `/positions`) — см. раздел «dYdX v4» ниже про детали каждого источника
  данных.
- `HTX_API_KEY` / `HTX_API_SECRET` (+ опционально `HTX_PROXY`) — см. раздел
  «HTX» ниже: интеграция на новом `/v5/...` API HTX (старый
  `/linear-swap-api/v1/...` отключён биржей 19.09.2026, см. раздел про
  реальный случай) добавляется по шагам, пока работают автозапись новых
  шорт-позиций, автоподбор цены/объёма/времени входа в калькуляторе,
  funding-отчёты (`/report`/`/calendar`/веб-калькулятор), автозаполнение
  столбца P и алерт о приближении убытка к марже счёта, остальное
  (ликвидационные алерты, детекция закрытия, `/rates`, сводный баланс)
  ещё не реализовано.
- `UNISWAP_WALLET_ADDRESS` / `ETHERSCAN_API_KEY` — для авто-подбора спот-цены
  входа по покупкам на Uniswap (см. раздел ниже про механизм поиска). Оба
  обязательны вместе — без одного из них Uniswap как источник просто
  пропускается, без ошибки.

Новые, для веб-калькулятора и алертов:

- `WEB_APP_USERNAME` — логин для входа на страницу калькулятора (по
  умолчанию `admin`).
- `WEB_APP_PASSWORD` — **обязательно задать**. Без него страница
  калькулятора отдаёт 500 и не показывается вообще — это осознанная защита
  от случайной публикации финансовых данных без пароля на публичном
  Railway-домене.
- `ALERT_CHECK_INTERVAL_MINUTES` — как часто проверять прогнозный funding
  по открытым позициям, по умолчанию `60`.
- `FUNDING_ALERT_THRESHOLD` — порог в долях (не в процентах), по умолчанию
  `0.0` (алерт при любой отрицательной прогнозной ставке).
- `SLTP_CHECK_INTERVAL_MINUTES` — как часто проверять закрытие позиций по
  стоп-лоссу/тейк-профиту, по умолчанию `2`.

Опционально, для синхронизации с Google Sheet (`sheets_sync.py`, см.
раздел ниже; без них поток синхронизации просто не запускается):

- `GOOGLE_SHEET_ID` — id таблицы (часть её URL между `/d/` и `/edit`).
- `GOOGLE_SERVICE_ACCOUNT_JSON` — содержимое JSON-ключа сервисного
  аккаунта Google целиком, одной строкой. Таблицу нужно один раз
  расшарить на email из поля `client_email` внутри этого JSON (права
  редактора) — без этого шага запись падает с 403.
- `GOOGLE_SHEET_TAB` — опционально, имя вкладки, по умолчанию берётся
  первая (единственная) вкладка в файле.
- `SHEET_SYNC_INTERVAL_MINUTES` — период синхронизации `sheets_sync.py`
  (столбец P), по умолчанию `60`.
- `SHORT_POSITION_CHECK_INTERVAL_MINUTES` — период проверки НОВЫХ
  шорт-позиций `short_position_tracker.py` (см. раздел ниже), по умолчанию
  `60`. Тот же GOOGLE_SHEET_ID/GOOGLE_SERVICE_ACCOUNT_JSON запускает оба
  потока сразу — интервалы у них при этом настраиваются НЕЗАВИСИМО.

Опционально, для страницы `/balances` и команды `/balance` (см. раздел
«Сводный баланс» ниже; без них биржи по-прежнему считаются в общем балансе —
не хватает только Aave/KuCoin):

- `RABBY_WALLET_ADDRESS` — адрес EVM-кошелька, на котором открыта Aave-
  позиция. Если не задан, но задан `UNISWAP_WALLET_ADDRESS` — используется он
  (обычно это один и тот же кошелёк).
- `ETHERSCAN_API_KEY` — тот же ключ, что и для поиска цены входа на Uniswap
  (см. выше); используется для Aave (сам баланс кошелька не сканируется, см.
  раздел ниже).
- `KUCOIN_API_KEY` / `KUCOIN_API_SECRET` / `KUCOIN_API_PASSPHRASE` (+
  опционально `KUCOIN_PROXY`) — все ТРИ значения обязательны вместе (у
  KuCoin, в отличие от остальных бирж, ключ подписи состоит из трёх частей,
  не двух — passphrase задаётся отдельно при создании ключа). Участвует
  наравне с остальными пятью биржами везде: сводный баланс (`balances.py`),
  авто-подбор спот-цены (`entry_price.py`), отслеживание новых шорт-позиций
  (`short_position_tracker.py`), калькулятор (`calculator.py`), `/positions`,
  `/report`/`/calendar`, `/rates`, фоновые алерты и автозаполнение столбца P
  (`sheets_sync.py`) — см. раздел «KuCoin в funding-контуре» ниже про
  единственную особенность (обязательный конкретный символ в её API) и про
  то, почему `/report`/`/calendar` для KuCoin дополнительно требуют
  `GOOGLE_SHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON` (остальное — нет).

## Калькулятор — как считает

Для выбранной биржи/монеты/периода:

```
net = funding_income − opening_fees + spread_effect
```

- `funding_income` — сумма фактических выплат funding по фьючерсной позиции
  за период (из истории биржи).
- `opening_fees` — komиссии открытия обеих ног: `qty × цена_спота ×
  spot_fee_pct + qty × цена_фьючерса × futures_fee_pct`. Ставки — taker,
  дефолты без VIP-скидок, **переопределяются вручную** в UI под свой
  аккаунт.
- `spread_effect` — `(цена_фьючерса − цена_спота) × qty`, ценовой спред
  между ценой исполнения фьючерсного шорта и спотовой покупки в момент
  открытия.

  Обе цены калькулятор пытается подобрать САМ при выборе конкретной монеты
  (не «все открытые позиции»): цена фьючерса — из данных текущей открытой
  позиции на бирже; цена споta — из истории сделок на всех подключённых
  спот-биржах (Bybit/MEXC/Gate — у Aster/Lighter споta нет вовсе) в окне
  времени вокруг момента открытия шорта (±20 мин, если биржа отдаёт точное
  время открытия — Bybit/MEXC; ±6 часов, если время оценено приблизительно
  по непрерывности funding — Aster/Gate/Lighter). Если подходящая
  спот-сделка не нашлась ни на одной бирже — поле остаётся пустым, и его
  нужно заполнить вручную. Оба поля в любом случае остаются редактируемыми
  перед расчётом.

### Поиск спот-цены на Uniswap (если задан `UNISWAP_WALLET_ADDRESS`)

У Uniswap (и у блокчейна вообще) нет REST-эндпоинта «моя история сделок по
паре», как у централизованных бирж — вместо этого ищем сами по истории
ERC-20-переводов кошелька: своп-покупка на Uniswap — это одна транзакция, в
которой есть ОДНОВРЕМЕННО исходящий перевод quote-актива (продали
USDC/USDT/WETH) и входящий перевод base-актива (получили купленную монету)
на/с адреса самого кошелька. Через какие пулы/хопы прошёл своп внутри —
не важно, это видно по крайним звеньям цепочки переводов.

Сеть заранее не фиксирована: опрашиваются ВСЕ майннет-сети, которые
поддерживает единый Etherscan V2 API (один и тот же `ETHERSCAN_API_KEY`
работает сразу на всех — сейчас это порядка 60 сетей, включая Arbitrum,
Base, Optimism, Polygon и т.д.), список сетей берётся динамически из
`/v2/chainlist` и кэшируется на сутки — так при добавлении Etherscan новых
сетей ничего в коде менять не придётся. На каждой сети смотрятся до 1000
последних ERC-20-переводов кошелька — для обычного кошелька этого с запасом
хватает на любое разумное окно поиска; если у кошелька на конкретной сети
очень высокая активность и нужная сделка вышла за пределы последних 1000
переводов — она не найдётся (сделано так специально ради скорости при
опросе полусотни сетей разом, а не через отдельные запросы для перевода
времени в номер блока на каждой). Из-за количества сетей автоподбор с
Uniswap в источниках может занимать до ~30 секунд.

Бесплатный тариф Etherscan — реально 3 запроса/сек на ключ (не 5, как можно
было бы подумать по документации — проверено на практике 24.08.2026), это
учтено троттлингом внутри `entry_price.py` с запасом.

**Важно: бесплатный тариф Etherscan покрывает не все сети.** По состоянию на
24.08.2026 бесплатный ключ отвечает «Free API access is not supported for
this chain» на части популярных сетей — в частности на **Base**, а также на
BNB Smart Chain, OP Mainnet, Avalanche C-Chain, Celo. Arbitrum на бесплатном
тарифе работает. Это ограничение самого Etherscan (нужен платный план для
полного покрытия), а не баг в коде. Такие сети (а также сети, на которых
исчерпан дневной лимит — «Community Free API Limit reached») запоминаются в
памяти процесса и не опрашиваются повторно до следующего обновления кэша
списка сетей (раз в сутки) — чтобы не тратить впустую время и не шуметь в
логах на каждый следующий поиск цены.

## KuCoin в funding-контуре

KuCoin теперь участвует наравне с Aster/Bybit/Lighter/MEXC/Gate везде:
калькулятор (`calculator.py`), `/positions`, `/report`/`/calendar`, `/rates`
и фоновые алерты по ставке/ликвидации/закрытию позиции, автозаполнение
столбца P. Особенность, из-за которой это потребовало отдельного механизма
(не пробел, а прямое следствие устройства API самой биржи):

**У всех остальных пяти бирж** приватный эндпоинт истории funding отдаёт
данные СРАЗУ ПО ВСЕМУ АККАУНТУ за период — можно узнать, что вообще
начислялось, не зная заранее список символов, включая уже закрытые позиции.
**У KuCoin** (`GET /api/v1/funding-history`, подтверждено офиц.
документацией и офиц. SDK `ccxt`) `symbol` — ОБЯЗАТЕЛЬНЫЙ параметр запроса:
получить "всё, что было начислено за эту неделю по любым символам" нельзя в
принципе, только "что было начислено по ВОТ ЭТОМУ конкретному символу".

Для `/positions`/калькулятора/столбца P/`/rates`/алертов это не проблема —
символ там и так уже известен заранее (текущая открытая позиция, либо выбор
пользователя в UI калькулятора): `fetch_kucoin_open_symbols` отдаёт точный
`openingTimestamp`, как `createdTime`/`createTime` у Bybit/MEXC, а для
прогнозной ставки (`/rates`) и цены (`GET /api/v1/funding-rate/{symbol}/
current`) используется публичный эндпоинт без ключей, тоже по известному
символу.

Но для `/report`/`/calendar` (сколько всего начислилось на аккаунте за
произвольный день/неделю/год) символ заранее НЕ известен — нужен список ВСЕХ
символов, которые когда-либо были активны, включая уже закрытые позиции.
Решение — **реестр символов** (`kucoin_symbol_history.py`, отдельная вкладка
"kucoin_symbols" в том же Google Sheet, тот же принцип, что и у
`aster_interval_history.py`): каждый час, побочным эффектом уже
существующей синхронизации столбца P (`sheets_sync.build_open_symbol_index`,
без единого лишнего запроса к бирже — список открытых позиций там и так уже
запрашивается), новый увиденный символ дописывается в реестр. `/report` и
`/calendar` затем опрашивают funding-историю по КАЖДОМУ когда-либо
виденному символу за запрошенный период (параллельно, один общий пул
потоков на все запросы сразу, до `WINDOW_FETCH_MAX_WORKERS`) — для давно
закрытых символов это просто вернёт пусто, а для активных в запрошенном
периоде — то же самое, что и один запрос "по всему аккаунту" у остальных
бирж.

**Требует Google Sheets** (`GOOGLE_SHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON`,
см. выше) — без них реестр негде хранить, и KuCoin в `/report`/`/calendar`
не появится (секция явно покажет "❌ Ошибка при получении данных", а не
тихий ноль) — так же, как и раньше. `/positions`, калькулятор, `/rates` и
все фоновые алерты по KuCoin от Google Sheets НЕ зависят и продолжают
работать в любом случае. Сразу после первого деплоя с этой функцией (или
если на KuCoin открылась совсем новая монета) реестр пуст/неполон — символ
появится в нём после ближайшего часового цикла синхронизации, с этого
момента `/report`/`/calendar` начнут его учитывать.

Побочный эффект того, что KuCoin теперь участвует в `funding_alerts.
get_open_positions()` (нужно было для `/rates`): фоновые алерты о закрытии
позиции (`sltp_alerts.py`) и о прогнозной ставке уходящей в минус
(`funding_alerts.py`) теперь срабатывают и для KuCoin — раньше закрытие
позиции на KuCoin эти циклы не отслеживали вовсе. Уточнение причины
закрытия (SL/TP) и цена закрытия фьючерса (столбец AE) для KuCoin
по-прежнему недоступны (тот же список бирж, что и раньше, см. «Алерты о
закрытии позиции» выше) — сам факт закрытия и цена закрытия на споте
(столбец AD, через уже существующий спот-поиск) при этом работают.

В калькуляторе (веб-UI и `/api/calculate`) для KuCoin по-прежнему
недоступен режим «все открытые позиции биржи» — нужно явно выбрать
конкретный символ, иначе `/api/calculate` вернёт понятную ошибку, а не
тихо неполный или нулевой результат (это не связано с реестром выше —
у калькулятора всегда был отдельный, более узкий запрос на конкретный
символ, реестр ему не нужен).

Дефолтная ставка комиссии в UI калькулятора для KuCoin — `0.06%` (taker,
VIP 0/tier 0, опубликовано на kucoin.com/vip/privilege/fee), как и для
остальных бирж — только отправная точка, переопределяется вручную.

## Отчёт за период (кнопка «📅 Календарь»)

Кнопка «📅 Календарь» (и команда `/calendar`) присылает интерактивный
календарь. Клик по числу — как и раньше, отчёт за этот ОДИН день. Под
сеткой дней — дополнительные кнопки для отчёта за ПЕРИОД:

- **🗓 7 дней / 🗓 30 дней / 🗓 365 дней** — скользящее окно НАЗАД от
  текущего момента (не календарные неделя/месяц/год) — явно число дней в
  подписи кнопки, чтобы не создавать ложных ожиданий про календарные
  границы периода.
- **📆 Диапазон (с даты по дату)** — переключает тот же календарь в режим
  выбора: сначала клик по НАЧАЛЬНОЙ дате, потом (тем же календарём,
  можно листать месяцы стрелками) — по КОНЕЧНОЙ. Обе даты включительно.
  Если перепутать порядок (кликнуть более раннюю дату второй) — бот
  молча переставляет их местами, а не показывает ошибку. Кнопка
  «❌ Отмена» в любой момент возвращает обычный календарь.

  Выбранная начальная дата "путешествует" через `callback_data` кнопок
  (например `cal:rend:2026-08-01:2026-08-15`) — бот не хранит состояние
  диалога у себя (ни в памяти процесса, ни в файле): вся необходимая
  информация уже есть в нажатой кнопке. Переживает рестарт Railway между
  двумя кликами без проблем — в отличие от подхода "запомнить, что
  выбрал этот chat_id", который сломался бы при передеплое между двумя
  кликами пользователя.

Отчёт за период отличается от отчёта за один день двумя вещами:

1. **Данные собираются "окнами".** У бирж есть жёсткий лимит на диапазон
   ОДНОГО запроса истории funding (не наше ограничение — биржи): Aster и
   Bybit — 7 дней, Lighter и Gate — 30, MEXC и KuCoin — 90. Отчёт за день
   всегда укладывается в лимит одним запросом (`fetch_all`), а период
   (неделя/месяц/год/диапазон) может быть длиннее — тогда используется
   `fetch_all_windowed` (тот же приём "нарезать на окна и склеить", что
   уже применялся для команды `/positions`, см. `_fetch_in_windows` в
   `funding_report.py`), поэтому периоды длиннее нескольких дней всё ещё
   собираются дольше одного дня (для года при 7-дневном окне Aster/Bybit —
   около полусотни запросов на каждую из этих двух бирж) — бот
   предупреждает об этом перед началом сбора. Окна одной биржи
   опрашиваются ПАРАЛЛЕЛЬНО (до `WINDOW_FETCH_MAX_WORKERS`, по умолчанию 4,
   одновременно — не все сразу, чтобы не упереться в rate-limit биржи),
   а не строго по одному, как раньше — это основное время сборки годового
   отчёта, параллельность сокращает его в разы. KuCoin устроен иначе — не
   один аккаунт-эндпоинт с окнами, а отдельный запрос на каждый известный
   символ (см. «KuCoin в funding-контуре» ниже) — но делит тот же общий
   пул потоков. Порядок записей в
   результате при этом не важен: `_trim_to_continuous_run` (нужен для
   Aster/Lighter/Gate, см. следующий пункт) сам сортирует их по времени.

   **Gate дополнительно не отдаёт историю глубже 179 дней в прошлое**
   (подтверждено реальной ошибкой биржи "from time exceeds 180-day
   limit") — это ограничение не диапазона одного запроса, а глубины
   вообще, независимо от общего периода. Для периода "365 дней" часть
   диапазона по Gate физически недоступна — бот не проваливается с
   ошибкой и не показывает эту часть как "прибыли не было" (что выглядело
   бы как реальный ноль), а явно дописывает предупреждение в текст
   отчёта, что именно по Gate и за какой отрезок данных не хватает.

2. **К отчёту прикладываются два графика** (только для периода — у
   отчёта за один день график не нужен, там и так одно число):
   - столбцы прибыли по каждому календарному дню периода (зелёный/
     красный — тот же смысл, что и у эмодзи 🟢/🔴 в тексте отчётов);
   - линия нарастающего итога за весь период.

   Оба — **без разбивки по биржам**, только общая сумма по всем биржам и
   активам вместе (согласовано явно: разбивка по биржам, как на графике
   APR у кнопки «📈 Открытые позиции», для периода в несколько месяцев
   была бы слишком плотной и нечитаемой). Данные для графиков берутся из
   уже полученных для текста отчёта записей (`funding_chart.daily_totals_msk`)
   — повторных запросов к биржам не делает. Если за какой-то день начислений
   не было — на графике это ноль, а не пропуск (иначе реальные "простои"
   выглядели бы как сжатая шкала времени, а не как "в этот день дохода не
   было").

## Сводный баланс (`balances.py`)

Отдельно от истории funding — просто сколько денег СЕЙЧАС лежит на каждом
источнике целиком (включая спот-баланс на биржах — там обычно лежит
долгоживущий лонг-хедж, не только фьючерсная маржа). Смотреть можно двумя
способами:

- страница **`/balances`** (тот же Basic Auth, что и у калькулятора) —
  подробно, с разбивкой по сетям/токенам кошелька;
- кнопка **💰 Баланс** (или команда `/balance`) в Telegram — коротко, сумма
  по каждому источнику.

Источники и как считается баланс:

- **Bybit** — у Bybit деньги могут лежать в ЧЕТЫРЁХ разных местах
  одновременно, каждое требует своего запроса (см. `fetch_bybit_balance` в
  `balances.py`):
  - Unified Trading Account (`totalEquity`, `/v5/account/wallet-balance`);
  - Funding-кошелёк (`accountType=FUND`) — депозиты по умолчанию оседают
    именно тут и не видны в Unified, пока их не перевести явно;
  - Earn — Flexible Savings и OnChain-стейкинг (`/v5/earn/position`),
    принципал позиции (накопленные, но ещё не забранные проценты
    сознательно не считаются — это ещё не деньги "на счету");
  - крипто-займы — `/v5/crypto-loan-common/position` отдаёт готовый агрегат
    `totalCollateral`/`totalDebt` (уже в USD — подтверждено реальным ответом
    API: соседство с полем `ltv` означает общий знаменатель для всех монет
    сразу). Если он пуст — fallback на `/v5/crypto-loan-flexible/ongoing-
    coin` (только долг по монетам, без залога — этот эндпоинт залог не
    отдаёт вовсе). Займ с фиксированным сроком
    (`/v5/crypto-loan-fixed/borrow-order-info`) не опрашивается — у него нет
    списка активных `orderId` для перебора; если у вас именно такой займ —
    сумма будет занижена.

  Разбивка по всем частям (с диагностикой: `error` ⚠️ — настоящее
  исключение, не хватает прав у ключа и т.п.; у крипто-займов ещё и `note`
  ℹ️ даже когда ошибки не было) видна на веб-странице `/balances` — не
  нужно лезть в логи Railway, чтобы понять, ПОЧЕМУ, например, Earn
  показывает $0. В текстовом отчёте `/balance` в Telegram — только одна
  итоговая строка на Bybit, без разбивки (подробности сознательно оставлены
  только на веб-странице, чтобы не захламлять чат). Частая причина нулей по
  Earn/займам при том, что остальное считается верно — у API-ключа Bybit не
  включены права на эти категории отдельно от Wallet/Trade (Bybit выдаёт
  права по продуктам отдельными переключателями в настройках ключа) —
  проверьте это в первую очередь, прежде чем считать ошибкой на стороне
  кода.
- **MEXC / Gate** — отдельно фьючерсный счёт и спот-счёт (два разных API со
  своей схемой подписи запроса каждый), складываются вместе. Спот-баланс
  оценивается через `price_spot_balances_usd_native()`: стейблкоины — по
  номиналу, остальное — **в первую очередь по публичному тикеру самой
  биржи** (`GET /api/v3/ticker/price` у MEXC, `GET /api/v4/spot/tickers` у
  Gate, пара `ASSET/USDT`), и только то, чего на бирже не нашлось —
  через CoinGecko как fallback (курируемый список + полный список тикеров,
  см. `_coingecko_symbol_to_id`/`price_spot_balances_usd` в `balances.py`).

  Раньше спот оценивался только через CoinGecko, и это дважды приводило к
  недосчёту: сначала — курируемый список из ~24 монет, где всё за его
  пределами молча выпадало из суммы; потом, после перехода на полный
  список тикеров CoinGecko — обратная проблема: у CoinGecko тикеры НЕ
  уникальны, и для малоизвестных/биржевых листингов (на реальном аккаунте
  — MEXC-токены BTW/GUA) поиск по тикеру зацепил ЧУЖУЮ монету с тем же
  символом, дав сильно заниженную (но формально "оценённую", без единой
  ошибки) цену. Цена с самой биржи, где эта монета реально куплена,
  однозначна и такой проблемы не имеет.

  Фьючерсный счёт Gate — `total` **+** `unrealised_pnl` (подтверждено
  официальной моделью `FuturesAccount` в `gateapi-go`: `total` явно
  исключает нереализованный PnL — тот же случай, что у Aster/Lighter ниже).
- **Aster** — баланс кошелька (`/fapi/v3/balance`) **+** нереализованный
  PnL открытых позиций (`/fapi/v3/positionRisk`, поле `unRealizedProfit`,
  как у Binance Futures API, форком которого является Aster). Спота у
  Aster нет вовсе.
- **Lighter** — `collateral` (обеспечение) **+** сумма `unrealized_pnl` по
  всем открытым позициям — по документации Lighter Total Account Value =
  Collateral + Unrealized PnL, готового поля с суммой в API нет. Спота у
  Lighter нет вовсе.

  Для всех трёх бирж (Gate/Aster/Lighter) раньше учитывался только сам
  кошелёк/collateral, без PnL открытых позиций — из-за этого баланс
  расходился с реальным, пока позиции были открыты (замечено на реальном
  аккаунте).
- **dYdX** — публичный Indexer API (без ключа, по адресу кошелька, тот же
  эндпоинт `/v4/addresses/{address}/subaccountNumber/{n}`, что используют
  `short_position_tracker`/`margin_alerts`/`entry_price`, см.
  `funding_report._dydx_subaccount_raw`). В отличие от Aster/Gate/Lighter
  выше, поле `equity` уже включает нереализованный PnL открытых позиций
  (та же особенность, что у KuCoin `accountEquity`) — прибавлять отдельно
  не нужно, задвоило бы PnL. Спота у dYdX нет вовсе — это чисто
  perpetual-биржа.
- **Aave v3** — ON-CHAIN, чистая стоимость позиции (обеспечение минус долг)
  через `Pool.getUserAccountData(address)`; сети — Ethereum/Arbitrum
  One/Base (адреса контрактов захардкожены в `AAVE_V3_POOL`, добавить сеть —
  одна строка).
- **KuCoin** — не часть funding-стратегии (нет в `funding_report.py`/
  `calculator.py`/`funding_alerts.py`), участвует только в сводном балансе.
  Отдельно фьючерсный счёт и спот-счёт, как у MEXC/Gate:
  - фьючерсы — `GET /api/v1/account-overview`, но, в отличие от Bybit
    UNIFIED (один запрос сразу на всё), у KuCoin нет эндпоинта "баланс по
    всем маржам сразу" — опрашивается по очереди каждая валюта маржи
    (USDT, USDC, XBT — так у KuCoin называется BTC для монеты-маржи).
    Валюта, в которой счёт не открыт, отдаёт ошибку — не то же самое, что
    "баланс 0", такая валюта просто пропускается. Поле `accountEquity` УЖЕ
    включает нереализованный PnL открытых позиций (подтверждено офиц.
    формулой `accountEquity = unrealisedPNL + marginBalance`) — в отличие
    от Aster/Gate/Lighter выше, добавлять PnL отдельно не нужно;
  - спот — `GET /api/v1/accounts` без фильтра отдаёт сразу ВСЕ счета
    (main — то же самое, что Funding-кошелёк у Bybit, деньги оседают там
    по умолчанию; trade — собственно спот; margin) одним запросом,
    суммируется по каждой монете;
  - цена спота — как у MEXC/Gate: сначала публичный тикер самой биржи
    (`GET /api/v1/market/allTickers`, пары вида `{ASSET}-USDT`), CoinGecko
    только как fallback (см. `fetch_kucoin_ticker_prices`).

  Схема подписи (`KC-API-SIGN`/`KC-API-PASSPHRASE`/`KC-API-KEY-VERSION=2`)
  подтверждена по офиц. SDK `ccxt` (`ccxt/kucoin.py`) — **не проверена на
  реальном ответе** API, как и остальные поля этой биржи, см. список ниже.

**Rabby wallet (баланс самого кошелька) сознательно не мониторится.** Первая
версия сканировала кошелёк on-chain по всем сетям Etherscan V2 — это было
медленно (десятки секунд на запрос) и на реальном аккаунте ломало отправку
отчёта в Telegram. Платный DeBank Open API решал бы это одним быстрым
запросом, но признан слишком дорогим для этого бота — решили убрать
сканирование кошелька из мониторинга целиком, а не чинить наполовину. Aave
(выше) по-прежнему считается — он использует тот же адрес кошелька, но не
требует сканировать сеть целиком, только один `eth_call` на сеть.

Fluid тоже не мониторится: у него нет простого REST API для чтения позиций,
только on-chain resolver-контракты со сложным, не до конца документированным
ABI (вложенные структуры) — разбирать их вслепую для финансового инструмента
рискованно.

**Spot Grid Bot на Bybit тоже не мониторится** (была попытка автоматизации,
убрана — см. git-историю). На практике, на реальном аккаунте, эндпоинты
Trading Bot API (`POST /v5/botsummary/list-all-bots`,
`POST /v5/grid/query-grid-detail`) отдавали `10005: Permission denied` даже
при включённых правах `Spot` на ключе — и этих эндпоинтов вообще нет в
самой полной сторонней библиотеке-обёртке над официальным V5 API
(`tiagosiebler/bybit-api`). Похоже, это не публичный API для сторонних
ключей вообще, а внутренний эндпоинт веб-версии/приложения Bybit с
сессионной авторизацией — дальше подбирать права ключа бессмысленно.

**MEXC Loans тоже не мониторится** — залоговое кредитование (BTC в залог,
займ в USDT, с LTV и ликвидацией), не путать с обычным `margin/loan` для
маржинальной торговли (это другой продукт с другим API). Публичного API
для него не нашлось нигде — ни в официальной документации MEXC, ни в
`ccxt` (самая полная сторонняя библиотека, знает только про `margin/loan`).
Проверено дважды, второй раз — по полному официальному Postman-коллекшену
MEXC V3 (`mexcdevelop/mexc-api-postman`, зеркало всей официальной
документации целиком) и по полному тексту `ccxt/mexc.py`: во всём
официальном списке эндпоинтов есть только `/api/v3/margin/*`
(margin-трейдинг), раздела под MEXC Loans нет вообще ни одного. Раз даже
намёка на путь эндпоинта нет — решили не гадать вслепую (в отличие от Grid
Bot на Bybit выше, где хотя бы сами эндпоинты были известны, просто
недоступны для сторонних ключей, и от крипто-займов на Bybit, где
эндпоинт официально существовал под другим разделом API — просто не
сразу нашли правильные поля). Если у вас открыт такой займ на MEXC —
залог/долг по нему в итоговую сумму не включены, считайте вручную.

**Не до конца проверено на реальных аккаунтах** (в отличие от остального
кода бота, который переиспользует уже боевые эндпоинты/подписи из
`funding_report.py`):
- `fetch_bybit_balance` (Funding-кошелёк) и `fetch_bybit_earn_balance` —
  поля подтверждены по документации Bybit v5, но не сверены на реальном
  ответе;
- `fetch_mexc_spot_balance` — у спот-API MEXC другая схема подписи, чем у
  фьючерсного;
- `fetch_aster_balance` — поле `unRealizedProfit` подтверждено по
  документации Binance Futures API (форк которого — Aster), но не сверено
  на реальном ответе именно Aster;
- `fetch_lighter_balance` — имена полей (`collateral`/`unrealized_pnl`)
  подтверждены по официальной документации SDK Lighter
  (elliottech/lighter-python), но не сверены на реальном ответе API.
- `fetch_kucoin_spot_balance`/`fetch_kucoin_futures_balance` — новее
  остальных, ни разу не сверены с реальным аккаунтом KuCoin. Формулы и
  имена полей подтверждены по офиц. SDK `ccxt` и офиц. Go SDK
  `Kucoin/kucoin-futures-go-sdk`, но не проверялись на реальном ответе.
  Если у вас старый API-ключ, созданный ДО перехода KuCoin на
  KC-API-KEY-VERSION=2 — заголовок `KC-API-PASSPHRASE` будет неверным
  (для версии 1 пассфраза передаётся как есть, без подписи); пересоздайте
  ключ или сообщите об этом явно, если увидите ошибку авторизации.

`fetch_bybit_crypto_loan_balance` (`totalCollateral`/`totalDebt`) —
подтверждено реальным ответом API, доверие высокое.

Сверьте оставшееся с соответствующим приложением на реальном аккаунте,
прежде чем полагаться на цифры.

## Алерты по открытым позициям

Раз в `ALERT_CHECK_INTERVAL_MINUTES` минут для каждой открытой сейчас
позиции запрашивается прогнозная (не историческая) ставка на СЛЕДУЮЩУЮ
выплату funding через публичные эндпоинты бирж. Алерт в Telegram уходит
один раз при переходе ставки из неотрицательной в отрицательную по паре
(биржа, символ) — не при каждой проверке, чтобы не спамить.

Ту же прогнозную ставку можно посмотреть в любой момент по запросу —
кнопка **🔮 Ставка финансирования** (или команда `/rates`) в Telegram
присылает её сразу по всем открытым позициям на всех биржах, а не только
когда она уходит в минус. Рядом с каждой позицией — ТЕКУЩАЯ (mark/fair)
цена актива и PnL, знак — от лица P&L шорта (у бота везде только шорты),
а не голого движения цены: цена ВЫШЕ входа — минус и 🔴 (убыток по шорту),
цена НИЖЕ входа — плюс и 🟢. В скобках рядом с ценой — **цена ЛИКВИДАЦИИ**
(явная просьба пользователя заменить ею цену входа, которая показывалась
там раньше — сам процент по-прежнему считается от цены входа, просто
число в скобках теперь другое):

```
🔴 BTWUSDT: -0.0120% за выплату (годовых -13.1%) — через 2ч 14м, funding раз в 8ч
   🔴 Цена: 0.0149 (-4.9% от входа, ликвидация 0.0151)
```

Источник цен — position-эндпоинты каждой биржи, те же, что уже проверены
для алертов о ликвидации (`liquidation_alerts.py`, переиспользуются через
импорт, не копируются заново, включая Lighter — см. «Алерты о приближении
к ликвидации» выше) — если для конкретного символа валидной цены
ликвидации не нашлось (например, кросс-маржа без изолированного риска по
конкретной позиции), в скобках останется только процент, без числа.
Прогнозная ставка для KuCoin — отдельный публичный эндпоинт `GET /api/v1/
funding-rate/{symbol}/current` (без ключей), интервал выплат берётся из
поля `granularity` в том же ответе (у KuCoin он документированно может
отличаться по символу, не зафиксирован на 8ч, как у большинства
остальных). Работает для **всех шести** подключённых бирж.

**MEXC, Gate и Lighter — отдельная ветка (явная просьба пользователя:
сначала MEXC, затем "сделай всё то же самое" для Gate и Lighter)**: вместо
% от цены входа показывается % от **поддерживаемой маржи счёта** — та же
формула, что и в алерте по марже (см. «Алерты о марже фьючерсного счёта»
выше). Причина — с плечом небольшое движение цены может быть значительным
процентом от маржи, а голый "% от цены входа" этого не показывает (и
наоборот — для низкого плеча большое движение цены может быть
незначительным относительно маржи). Диспетчер `_MARGIN_PNL_FETCHERS` в
`funding_alerts.py` — по записи на биржу, рассчитан на дальнейшее
расширение.

Для **MEXC**: `margin_base = cashBalance + positionMargin` (оба поля НЕ
зависят от `unrealized`, проверено на реальных данных счёта). Долларовый
PnL считается как `qty_coins * (entry - mark)` (шорт: прибыль при падении
цены), где `qty_coins = holdVol * contractSize` — `holdVol` у MEXC в
КОНТРАКТАХ, не в монетах (`entry_price._fetch_mexc_contract_size`, тот же
хелпер, что уже используется в `short_position_tracker.py`):

```
🔴 BTWUSDT: -0.0120% за выплату (годовых -13.1%) — через 2ч 14м, funding раз в 8ч
   🔴 PnL: -169.40 (-42.8% от маржи) — цена: 0.0149 (ликвидация 0.0151)
```

(Реальные данные счёта: cashBalance=0.369, positionMargin=395.458 →
margin_base=395.83, 42.8% = 169.40/395.83.) Цена ликвидации в скобках —
здесь это ОТДЕЛЬНЫЙ запрос (margin-pnl-фетчер её не отдаёт, см.
«Алерты о марже фьючерсного счёта» выше), через те же `_PRICE_FETCHERS`,
что и у остальных бирж.

Для **Gate**: `margin_base = total` (уже сам сумма position_margin+
order_margin+available, не зависит от unrealised_pnl). Долларовый PnL — не
нужно вычислять через количество/цену: Gate отдаёт его прямо в ответе
позиций (поле `unrealised_pnl`, ПОДТВЕРЖДЕНО офиц. докам), проще и
надёжнее, чем для MEXC:

```
🔴 GUA_USDT: -0.0100% за выплату (годовых -10.9%) — через 1ч 2м, funding раз в 8ч
   🟢 PnL: +50.00 (+10.0% от маржи) — цена: 0.045 (ликвидация 0.08)
```

Для **Lighter**: `margin_base = collateral` (аккаунт, не зависит от
unrealized_pnl, тот же смысл, что cashBalance+positionMargin у MEXC и
total у Gate). Долларовый PnL, как и у Gate, отдаётся прямо в ответе
позиции (поле `unrealized_pnl`, тот же источник, что уже использует
`balances.fetch_lighter_balance`). **ВАЖНО**: в отличие от MEXC/Gate, эта
формула не проверена против реального счёта с открытой позицией — поля
взяты из офиц. docs SDK (`elliottech/lighter-python`, проверено
06.10.2026), но собственной проверки по диагностическому логу сырых полей
(как была для MEXC) для Lighter не делалось:

```
🔴 ANSEM: -0.0100% за выплату (годовых -87.6%) — через 1ч, funding раз в 1ч
   🔴 PnL: -250.00 (-83.3% от маржи) — цена: 0.18 (ликвидация 0.20)
```

Если получить маржу счёта не удалось (сбой API) — показывается старое
"% от цены входа" как fallback, чтобы строка не осталась вовсе без PnL.
Для остальных трёх бирж (Bybit/Aster/KuCoin) PnL/%Маржи по-прежнему не
отслеживаются (поведение не менялось), но цена ликвидации в скобках
теперь заменяет цену входа и для них.

## График APR по открытым позициям — история интервала funding на Aster

График годовой ставки (кнопка «📈 Открытые позиции») строит APR из
исторических ставок funding, приводя их к годовым через реальный интервал
начисления (`funding_alerts.annualize`). У Aster этот интервал по умолчанию
8 часов, но биржа имеет задокументированное право временно СОКРАЩАТЬ его
(до 1-4ч) при экстремальной волатильности по символу — а публичная история
ставок (`GET /fapi/v1/fundingRate`) не сообщает, какой интервал действовал
в конкретный момент, только сам факт ставки. Раньше график брал ТЕКУЩИЙ (на
момент построения) интервал символа и применял его ко всей истории этого
символа разом — из-за этого график, построенный, пока короткий интервал ещё
действовал, и график, построенный уже после того как интервал вернулся к
8ч, показывали для ОДНИХ И ТЕХ ЖЕ прошлых дат совершенно разный APR (реальный
случай — см. историю чата, сентябрь 2026).

Исправлено частично, на будущее: `aster_interval_history.py` каждые
`ALERT_CHECK_INTERVAL_MINUTES` минут (побочным эффектом уже существующего
цикла алертов, без лишних запросов к бирже) записывает в отдельную вкладку
Google Sheet ("aster_funding_intervals") текущий интервал по каждому
открытому символу, но ТОЛЬКО когда он меняется — компактная история
переходов. Дальше график APR подставляет для каждой точки истории
интервал, ДЕЙСТВОВАВШИЙ на тот момент по этим наблюдениям, а не всегда
текущий. Историю ДО появления этой вкладки восстановить нечем — это
ограничение публичного API Aster, не бот может её "досчитать" задним
числом; для дат раньше первого наблюдения используется дефолт 8ч
(`ASTER_DEFAULT_FUNDING_INTERVAL_HOURS`), как и было. У Gate теоретически
та же особенность, но её не трогали — просьба была именно про Aster.

**Цвет линии — на каждую позицию, не на всю биржу** (явная просьба
пользователя — две одновременно открытые позиции на Lighter сливались в
одну линию одного цвета). Первая по алфавиту символа позиция на бирже
сохраняет привычный "базовый" цвет этой биржи (`EXCHANGE_COLORS` — тот же,
что показывался раньше для единственной позиции); вторая и далее позиции
на той же бирже берут следующий цвет из общего пула `EXTRA_SERIES_COLORS`
(оранжевый → синий → фиолетовый). Все 8 цветов подобраны и проверены
скриптом dataviz-скилла на различимость при обычном зрении (порог ΔE≥15
между любой парой пройден); легенда с прямой подписью "Биржа: СИМВОЛ" у
каждой линии, как и раньше, остаётся обязательным вторым способом
идентификации (не только цвет).

## Алерты о приближении к ликвидации

`liquidation_alerts.py` раз в `LIQUIDATION_CHECK_INTERVAL_MINUTES` минут
(по умолчанию 5) сравнивает для каждой открытой позиции текущую (mark/fair)
цену с ценой ВХОДА и ценой ЛИКВИДАЦИИ. Расстояние вход→ликвидация — это
"запас прочности" позиции; когда цена прошла ПРОТИВ позиции (у бота только
шорты — значит, вверх) `LIQUIDATION_ALERT_THRESHOLD` (по умолчанию 0.70 =
70%) этого расстояния, приходит алерт в Telegram:

```
🚨 MEXC BTWUSDT: цена прошла 75% пути от входа до ликвидации
Вход: 0.0142 → сейчас: 0.0149 → ликвидация: 0.0151
```

Как и с прогнозным funding — алерт **edge-triggered**: уходит один раз при
переходе доли пройденного пути из "меньше порога" в "порог и больше" по
паре (биржа, символ), а не на каждой проверке подряд, пока позиция
остаётся в опасной зоне; как только доля падает обратно ниже порога —
состояние сбрасывается, и следующий заход в опасную зону снова пришлёт
алерт.

Поддерживается для **всех шести бирж, включая Lighter** (явная просьба
пользователя — "настрой Lighter так же, как MEXC и Gate"). У Bybit/Aster/
Gate/KuCoin/MEXC — подтверждённое поле цены ликвидации в ответе позиций
(`liqPrice`, `liquidationPrice`, `liq_price`, `liquidationPrice`,
`liquidatePrice` соответственно) и, кроме MEXC, там же и текущая
(`markPrice`/`mark_price`) — для MEXC она берётся отдельным публичным
запросом `GET /api/v1/contract/fair_price/{symbol}`.

**Lighter** — раньше считалось неподдерживаемым (ни офиц. SDK, ни
документация не называли поле цены ликвидации), но это было верно только
на момент той проверки: офиц. SDK (`elliottech/lighter-python`,
`docs/AccountPosition.md`, дословно проверено 06.10.2026) с тех пор
получил поле `liquidation_price` прямо в ответе позиции (`GET /api/v1/
account`), рядом с `avg_entry_price`; текущая цена — тот же публичный
`fetch_lighter_mark_prices()`, что уже используется в `/rates`.
**ВАЖНО**: это поле, в отличие от остальных пяти бирж, НЕ проверено
против реального счёта с открытой позицией (доступа к боевому
Lighter-аккаунту из среды разработки нет) — та же оговорка, что уже стоит
у поля `sign` (определение шорта) в `short_position_tracker.py`. Первый
реальный алерт по Lighter стоит явно сверить с тем, что показывает само
приложение Lighter.

Позиции с некорректными для шорта данными (цена ликвидации не выше цены
входа — например, кросс-маржа без изолированного риска по конкретной
позиции у Binance-совместимых API) просто пропускаются, без алерта и без
ошибки — это не баг, а особенность данных биржи в этом режиме маржи.

Как и в `sltp_alerts.py`/`funding_alerts.py`, временный сбой запроса
позиций на одной бирже не сбрасывает state по остальным её символам —
та же защита от ложных срабатываний, что уже потребовалась после
реального бага с MEXC BTW_USDT (см. ниже).

## Алерты о марже фьючерсного счёта

`margin_alerts.py` раз в `MARGIN_CHECK_INTERVAL_MINUTES` минут (по
умолчанию 5) проверяет не отдельную позицию, а СЧЁТ целиком: насколько
нереализованный убыток съел поддерживаемую маржу на фьючерсном счёте.
**MEXC, Gate и Lighter** (явная просьба — сначала "Сначала по бирже MEXC",
затем "сделай всё то же самое" для Gate и Lighter), структура
(`_MARGIN_FETCHERS`, как и `_LIQUIDATION_POSITION_FETCHERS` выше)
рассчитана на расширение на другие биржи без переделки логики.

Формула проверена на РЕАЛЬНЫХ сырых данных счёта пользователя (после двух
неверных попыток через `equity` и через `cashBalance - unrealized`):

```
margin_base = cashBalance + positionMargin
```

Обе величины — сырые поля того же ответа `GET /api/v1/private/account/
assets`, НЕ зависящие от текущего `unrealized` PnL: `cashBalance`
("Withdrawable balance") — свободные, не занятые ни одной позицией
деньги; `positionMargin` — маржа, уже заложенная под открытую позицию.
Их сумма — весь РЕАЛЬНЫЙ капитал на фьючерсном счёте (не считая floating
PnL), который не скачет вместе с текущей ценой — только от депозита/
вывода или изменения размера позиции.

Проверено на диагностическом логе сырых полей реального счёта
(2026-10-05): `cashBalance=0.369`, `positionMargin=395.458`,
`unrealized=-169.40`, `equity=226.43` → `margin_base ≈ 395.83`.
Пользователь подтвердил это число ("228-(-167)=395" — 228 на экране это
`equity` в момент снятия показаний, а `equity - unrealized = cashBalance
+ positionMargin` — то же тождество, другими словами).

Алерт срабатывает, когда `unrealized` отрицателен и его модуль достиг
`MARGIN_ALERT_THRESHOLD` (по умолчанию 0.70 = 70%) от `margin_base`:

```
🚨 MEXC (USDT): нереализованный убыток достиг 80% от маржи на счёте
Маржа: 500 USDT → нереализованный PNL: -400 USDT
```

В отличие от двух предыдущих версий, у ЭТОЙ формулы `margin_base` НЕ
зависит от `unrealized` — поэтому нет самореференции знаменателя: порог
70% — это ровно 70% от реального, статичного капитала счёта, без побочных
математических эффектов.

**GATE** — та же идея, аналогичные поля того же ответа `GET /api/v4/
futures/{settle}/accounts` (ПОДТВЕРЖДЕНО по офиц. докам Gate API v4):

```
margin_base = total   (total = position_margin + order_margin + available)
unrealized  = unrealised_pnl
```

Здесь `total` УЖЕ сам является нужной суммой — Gate официально
документирует его как `position_margin + order_margin + available`, то
есть весь капитал счёта без floating PnL, который отдаётся отдельным
полем `unrealised_pnl`. Никакого дополнительного сложения полей не
требуется, в отличие от MEXC:

```
🚨 Gate (USDT): нереализованный убыток достиг 80% от маржи на счёте
Маржа: 500 USDT → нереализованный PNL: -400 USDT
```

**LIGHTER** — тоже одно готовое поле, как у Gate:

```
margin_base = collateral
unrealized  = sum(position.unrealized_pnl)
```

`collateral` (ПОДТВЕРЖДЕНО офиц. docs SDK `elliottech/lighter-python`,
`docs/Account.md`, проверено 06.10.2026) — обеспечение на уровне аккаунта
БЕЗ учёта floating PnL, тот же смысл, что `cashBalance+positionMargin` у
MEXC и `total` у Gate. `unrealized` считается суммой поля
`unrealized_pnl` по всем открытым позициям (тот же источник, что уже
использует `balances.fetch_lighter_balance`). **ВАЖНО**: в отличие от
MEXC/Gate, эта формула НЕ проверена против реального счёта пользователя с
открытой позицией (диагностического лога сырых полей, как был для MEXC,
для Lighter не делалось) — первый реальный алерт стоит явно сверить с
суммами на экране приложения Lighter:

```
🚨 Lighter (USDC): нереализованный убыток достиг 78% от маржи на счёте
Маржа: 300 USDC → нереализованный PNL: -235 USDC
```

**DYDX** — некастодиальная биржа, формула на базе другого набора полей
(Indexer API, саб-аккаунт):

```
margin_base = equity
unrealized  = sum(position.unrealizedPnl)
```

В ОТЛИЧИЕ от MEXC/Gate/Lighter, `equity` у dYdX УЖЕ включает floating
PnL (Indexer не отдаёт отдельного поля "капитал без PnL") — порог 70%
здесь означает "убыток съел 70% текущего equity", а не "70% от
статичного капитала без PnL", как у остальных трёх бирж:

```
🚨 dYdX (USDC): нереализованный убыток достиг 80% от маржи на счёте
Маржа: 1000 USDC → нереализованный PNL: -800 USDC
```

Как и с ликвидацией — алерт **edge-triggered** по паре (биржа, валюта
счёта): уходит один раз при переходе доли убытка из "меньше порога" в
"порог и больше", сбрасывается при восстановлении (включая выход в плюс),
и временный сбой API биржи не сбрасывает state по ошибке (та же защита,
что и в `liquidation_alerts.py`).

## dYdX v4 — текущий охват интеграции

dYdX v4 подключается только через `DYDX_ADDRESS` (+ опционально
`DYDX_SUBACCOUNT_NUMBER`) — биржа некастодиальная (on-chain), позиции и
баланс саб-аккаунта читаются ПУБЛИЧНО через её Indexer API по адресу
кошелька, без API-ключа и подписи запроса (подтверждено офиц.
docs.dydx.xyz и живым запросом к Indexer). Тикер символа — вида
`SEI-USD` (база + `-USD`, а не `-USDT`/`-USDC`, как у остальных бирж).

Работает:
- **автозапись новой строки в Google Sheet** при открытии шорта
  (`short_position_tracker.py`) — то, из-за чего dYdX вообще понадобился:
  до этой интеграции бот про dYdX не знал совсем, и открытые на нём шорты
  не попадали в таблицу автоматически;
- **алерт о приближении убытка к марже счёта** (`margin_alerts.py`, см.
  выше) — тот же порог 70%, что и для MEXC/Gate/Lighter;
- **детекция закрытия позиции** (`sltp_alerts.py`) — Telegram-алерт о
  закрытии и запись даты закрытия (столбец F) + попытка найти цену
  закрытия на споте (столбец AD, через общий для всех бирж поиск продажи
  на подключённых спот-биржах);
- автоподбор цены/времени входа в калькуляторе (`entry_price.py`);
- **`/rates`: PnL и % от поддерживаемой маржи счёта** (`margin_base =
  equity`, та же формула, что в алерте выше) — mark-цена берётся отдельным
  запросом `oraclePrice` рынка (Indexer не отдаёт её в самой позиции);
- **прогнозная ставка funding** (фоновый алерт об отрицательной ставке +
  строка в `/rates`) — `nextFundingRate` рынка (тот же `GET /v4/
  perpetualMarkets?market={ticker}`, что и `oraclePrice`), интервал
  фиксирован протоколом на 1 час для ВСЕХ рынков без исключений
  (ПОДТВЕРЖДЕНО офиц. docs.dydx.xyz/concepts/trading/funding: "We charge
  funding rates every hour... calculated at the end of each hour") — тот
  же случай, что уже есть у Lighter, не запрашивается отдельно. Время
  следующей выплаты не отдаётся API напрямую — вычисляется как следующая
  целая граница часа по UTC (там же, где "начинается funding-tick epoch"
  по докам), а не угадывается;
- **автозаполнение столбца P** (funding с момента открытия ТЕКУЩЕЙ позиции,
  `sheets_sync.compute_funding_total`) и то же самое для `/positions`
  (`funding_report.fetch_all_time_open_positions`) — **НЕ** ручное
  суммирование `fundingPayments`, а готовое поле `netFunding` прямо на
  объекте позиции в `openPerpetualPositions` (тот же `GET /v4/addresses/
  {address}/subaccountNumber/{n}`, что уже используется для баланса/
  открытых шортов/цены входа — ПОДТВЕРЖДЕНО офиц. схемой Indexer API,
  `api-documentation.md` в `dydxprotocol/v4-chain`: `netFunding` — сосед
  `sumOpen`/`sumClose`/`realizedPnl`, то есть это тот же накопительный
  учёт, что ведёт сам indexer, и то самое число, которое показывает
  официальный интерфейс dYdX). РЕАЛЬНЫЙ СЛУЧАЙ, из-за которого перешли на
  это поле: столбец P для SEI-USD показывал $3.19 (ручная сумма записей
  `fundingPayments` с момента открытия), а в интерфейсе dYdX та же позиция
  показывала $2.23 — расхождение устранено переходом на `netFunding`
  вместо попытки найти причину разницы в ручном подсчёте (см.
  `fetch_dydx_net_funding`). Калькулятор/`/report`/`/calendar`
  (`calculator.fetch_funding_history`, `EXCHANGE_FIELDS`/`EXCHANGE_LABELS`,
  список подключённых бирж `/api/exchanges` веб-калькулятора) по-прежнему
  суммируют `GET /v4/fundingPayments` вручную — там нужна сумма за
  ПРОИЗВОЛЬНЫЙ период (например, "за неделю"), а не "с момента открытия",
  `netFunding` для этого не подходит (верхней границы периода у него нет).
  `fundingPayments` (ПОДТВЕРЖДЕНО живым запросом к Indexer): отдаёт
  `payment` уже со знаком относительно держателя позиции (тот же смысл,
  что `unrealized_pnl` у Lighter/`change` у Gate — пересчитывать не
  нужно), сортировка по убыванию времени, фильтр по времени — только
  нижняя граница (`afterOrAt`), верхней границы в API нет вовсе, поэтому
  верхняя граница периода применяется на стороне бота, а пагинация идёт
  постранично до первой страницы старше начала периода;
- **цена закрытия фьючерса (столбец AE)** и **причина закрытия (SL/TP)**
  в `sltp_alerts.py` — `GET /v4/fills` для цены (ПОДТВЕРЖДЕНО живым
  запросом: явное поле `side`, тот же надёжный случай, что у Bybit/Aster
  — закрытие шорта = `side: "BUY"`, фильтруется напрямую, в отличие от
  MEXC/Gate, где стороны не фильтруются вовсе) и `GET /v4/orders?
  status=FILLED` для причины (поле `type` — `STOP_MARKET`/`STOP_LIMIT`
  → SL, `TAKE_PROFIT`/`TAKE_PROFIT_MARKET` → TP, ПОДТВЕРЖДЕНО офиц.
  docs.dydx.xyz/types/order_type). У `/v4/fills`, в отличие от
  `/v4/fundingPayments`, наоборот — только ВЕРХНЯЯ граница по времени
  (`createdBeforeOrAt`), нижней в API нет вовсе — фильтруется на
  стороне бота тем же приёмом (пагинация до первой страницы старше
  начала окна). РЕАЛЬНЫЙ СЛУЧАЙ (19.10.2026, прод): сервер стал отдавать
  400 Bad Request ("marketType must be provided if market is provided")
  на запрос с параметром `market` без `marketType` — похоже, изменение в
  валидаторе API dYdX (раньше поле не было обязательным). Из-за этого при
  закрытии позиции по SEI-USD не удалось получить цену закрытия (AE) —
  столбец записался без неё. Исправлено добавлением `marketType:
  "PERPETUAL"` (единственный тип рынка, которым торгует бот) в запрос;
- **цена ликвидации** (`liquidation_alerts.py` + в скобках в `/rates`) —
  единственный пункт из всего списка, где Indexer НЕ отдаёт нужное
  значение готовым полем ни для одной позиции (в отличие от всех
  остальных пяти бирж). Вычисляется по ОФИЦИАЛЬНО ЗАДОКУМЕНТИРОВАННОЙ
  формуле (docs.dydx.xyz/concepts/trading/liquidations, "Cross
  Liquidation Price") — проверено против ОБОИХ числовых примеров самой
  документации (isolated: equity=1000, шорт 3 ETH @3000, MMF=5% →
  liq≈3174.60; cross: + лонг 1000 STRK @1.75, MMF=10% → liq≈3380.95),
  совпадение с точностью до 6 знаков:
  ```
  MMR_o = Σ |size_i| * entry_i * MMF_i   (по ВСЕМ ОСТАЛЬНЫМ открытым
          позициям саб-аккаунта — общий margin-пул cross-режима)
  liq   = (equity - size*entry - MMR_o) / (|size|*MMF - size)
  ```
  Для единственной открытой на dYdX позиции (самый частый случай) MMR_o=0,
  и формула сводится к "Isolated Liquidation Price" из тех же докс.
  ОГОВОРКА: не различает рынки с ISOLATED margin type (их margin не
  делится с остальным саб-аккаунтом вовсе) — если на dYdX одновременно
  открыта ISOLATED-позиция, результат для ОСТАЛЬНЫХ позиций может быть
  неточным; для случая "одна позиция на dYdX" это не имеет значения;
- **`/report`/`/calendar`/`/positions`** — ежедневный/периодический
  Telegram-отчёт по ВСЕМ биржам сразу и сводка по текущим открытым
  позициям (`funding_report.fetch_all`/`fetch_all_windowed`/
  `fetch_all_time_open_positions`/`build_report`/
  `build_open_positions_report`) — отдельная, жёстко прописанная по
  каждой бирже вручную часть кода (не через общий `calculator.
  fetch_funding_history`, который для столбца P и веб-калькулятора
  подключён отдельно, см. выше), но тот же `fetch_dydx` переиспользуется
  и здесь. dYdX попадает в ту же категорию, что Bybit/MEXC — точное
  время открытия позиции прямо из API (`createdAt`), без нужды в
  приближённой оценке по непрерывности начислений funding.

Этим список полностью закрыт — dYdX интегрирован во все те же команды и
фоновые механизмы, что и остальные пять бирж, без исключений.

## HTX — текущий охват интеграции

HTX подключается через `HTX_API_KEY`/`HTX_API_SECRET` (+ опционально
`HTX_PROXY`) — обычная централизованная биржа с API-ключом (в отличие от
dYdX), со СВОЕЙ, отдельной от остальных бирж в проекте, классической
схемой подписи Huobi/HTX (`Signature` — ещё один query-параметр, а не
заголовок, HMAC-SHA256+base64; подробности — докстринг секции "Получение
данных с HTX" в `funding_report.py`).

**ВАЖНО, РЕАЛЬНЫЙ СЛУЧАЙ (19.10.2026, прод):** интеграция изначально была
написана под "старый" API HTX (`/linear-swap-api/v1/.../v3/...`). HTX
официально объявила (htx.com/support/65042754281336) полный перенос ВСЕХ
приватных интерфейсов фьючерсов на новый `/v5/...` API, с дедлайном
миграции **19.09.2026** — уже прошедшим к моменту написания этого раздела.
Первый же реальный запрос (`margin_alerts`, `swap_cross_account_info`) упал
в проде с `error_code 6023: "The current API version has expired. Please
upgrade to the V5 interface"`. Весь код ниже уже переписан под `/v5/...` —
схема подписи НЕ изменилась (ПОДТВЕРЖДЕНО открытым кодом ccxt,
`ccxt/htx.py`: v5-эндпоинты используют тот же HMAC-алгоритм), поменялись
только пути, метод (GET вместо POST) и поля ответа. Публичные рыночные
эндпоинты (`GET .../swap_contract_info`) миграция не затронула — объявление
HTX явно их исключает ("with the exception of market data interfaces").
Код НЕ проверен на реальном ответе API (нет доступа к аккаунту из среды
разработки) — первое реальное срабатывание каждого источника стоит
сверить с приложением HTX.

Интеграция добавляется по шагам (как и было с dYdX) — реализовано пока
только то, с чего начинался сам запрос на добавление биржи:

Работает:
- **автозапись новой строки в Google Sheet** при открытии шорта
  (`short_position_tracker.py`) — `direction == "sell"` на `GET
  /v5/trade/position/opens` (только режим cross margin — isolated не
  фильтруется отдельно, см. докстринг `_htx_positions_raw`);
- автоподбор цены/объёма/ВРЕМЕНИ входа в калькуляторе (`entry_price.py`,
  `_htx_position_entry`) — в отличие от старого API, `/v5/trade/position/
  opens` отдаёт `created_time` (точное время открытия) прямо в ответе,
  поэтому HTX попадает в ту же категорию, что Bybit/MEXC/KuCoin/dYdX
  (`_EXACT_TIME_EXCHANGES`), а не в "непрерывность начислений", как было
  бы со старым API;
- **funding-отчёты** (`/report`, `/calendar`, веб-калькулятор) —
  `GET /v5/account/bills`, `type=30,31` (funding fee income/expenditure —
  ПОДТВЕРЖДЕНО офиц. документацией прямо в расшифровке параметра `type`,
  та же расшифровка, что была у старого API). `margin_account` в новом
  API вообще не параметр — вместо него опциональный `margin_mode`
  (`HTX_MARGIN_MODE = "cross"`), `contract_code` тоже опционален — можно
  запросить funding сразу по всем контрактам одним запросом, в отличие от
  KuCoin. Лимиты окна/глубины запроса, что были у старого API (48ч/90
  дней), новая документация явно не переподтверждает (говорит только про
  значения по умолчанию) — оставлены те же консервативные значения "про
  запас" (`_EXCHANGE_WINDOW_DAYS["htx"] = 2`,
  `_EXCHANGE_MAX_LOOKBACK_DAYS["htx"] = 89`). Знак funding выставляется
  ЯВНО по типу записи (income — всегда `+`, expenditure — всегда `−`), а
  не берётся из сырого поля `amount` как есть — офиц. документация
  подтверждает только разбивку по типам, не сам знак числа в ответе (см.
  докстринг `fetch_htx` про то, почему это безопаснее непроверенного
  предположения в финансовом коде);
- **автозаполнение столбца P** (`sheets_sync.py`) — как и у Bybit/MEXC/
  KuCoin/dYdX, старт периода = точное время открытия позиции
  (`_EXACT_TIME_EXCHANGES`), без приближённой обрезки по непрерывности;
- **алерт о приближении убытка к марже счёта** (`margin_alerts.py`) —
  `GET /v5/account/balance` возвращает ОДИН объект на весь аккаунт (не
  список, как в старом API), с разбивкой по валютам в `details`. Готового
  поля "статический капитал без PnL" (`margin_static`, было в старом API)
  в новом ответе нет — `margin_base = equity - profit_unreal` вычисляется
  вручную на каждую валюту. `equity`/`profit_unreal` у HTX включают cross
  и isolated вперемешку (отдельного cross-only среза нет) — для этого
  бота не проблема на практике (isolated margin не используется);
- **`/rates` — прогнозная ставка funding** (`funding_alerts.py`) — через
  `GET /linear-swap-api/v1/swap_funding_rate` (ПУБЛИЧНЫЙ эндпоинт, без
  подписи, не затронут миграцией на v5 — см. выше, объявление HTX явно
  исключает рыночные данные). Берётся поле `funding_rate` (уже
  зафиксированная ставка на ближайшую выплату), а НЕ `estimated_rate`
  (отдельная, непрерывно обновляемая оценка текущего периода — другая
  семантика). Интервал выплат — фиксированный дефолт 8ч (стандартный цикл
  HTX, 00:00/08:00/16:00 по Сингапуру/GMT+8, подтверждено офиц. docs, FAQ
  "Settlement") — сам эндпоинт интервал не отдаёт. PnL и % от
  поддерживаемой маржи счёта (а не от цены входа — HTX зарегистрирован в
  `_MARGIN_PNL_FETCHERS`, как MEXC/Gate/Lighter/dYdX) — `profit_unreal`
  прямо в ответе позиций, `margin_base` — та же формула `equity -
  profit_unreal`, что и в алерте о марже (см. выше). Цена ликвидации в
  скобках — через `_PRICE_FETCHERS`/`_htx_liquidation_positions` (см.
  следующий пункт);
- **алерт о приближении к ликвидации** (`liquidation_alerts.py`) —
  `GET /v5/trade/position/opens` отдаёт `open_avg_price`/
  `liquidation_price`/`mark_price` — ВСЕ ТРИ прямо в одном ответе (в
  отличие от старого API, где `liquidation_price` не было вообще, и в
  отличие от dYdX, где цену ликвидации приходится вычислять по формуле,
  а цену — запрашивать отдельно) — ни одного доп. запроса не нужно.
  `mark_price` не упомянут в таблице описания полей офиц. докстринга HTX,
  но присутствует в её же Success Example — расхождение самой
  документации, подтверждено прямой цитатой примера ответа, не наше
  предположение;
- **сводный баланс** (`balances.py`, `/balances` и `/balance` в Telegram) —
  фьючерсный (`fetch_htx_futures_balance` — сумма `equity` по валютам
  счёта, та же формула, что и для PnL/маржи выше, но БЕЗ вычитания
  `profit_unreal`: здесь нужен полный капитал С floating PnL, а не
  "статическая" маржа) и спот-баланс. Спот-API HTX — ДРУГОЙ хост
  (`api.huobi.pro`, не `api.hbdm.com` у фьючерсов), но ТА ЖЕ классическая
  схема подписи (ПОДТВЕРЖДЕНО офиц. документацией: "The API key is shared
  for all instruments in Huobi including spot, futures, swap, options") —
  `funding_report._htx_sign` параметризован host'ом, чтобы не копировать
  логику подписи заново (`balances._htx_spot_signed_get`). Баланс — через
  `GET /v1/account/accounts` (чтобы узнать `account-id` типа `"spot"`,
  кэшируется в памяти процесса — не меняется) + `GET /v1/account/
  accounts/{id}/balance` (сумма по `type` `"trade"`+`"frozen"` на каждую
  валюту, тот же принцип, что и у KuCoin). Цена монет на споте — сначала
  публичный тикер самой HTX (`GET /market/tickers`, `fetch_htx_ticker_
  prices`), CoinGecko — только как fallback (тот же принцип, что у MEXC/
  Gate/KuCoin, см. докстринг `price_spot_balances_usd` про коллизию
  тикеров). НЕ ПРОВЕРЕНО на реальном счёте (нет доступа к аккаунту из
  этой среды разработки);
- **детекция закрытия позиции + цена закрытия/причина SL-TP**
  (`sltp_alerts.py`) — сам факт закрытия ловится автоматически (общий
  механизм, сравнивающий списки открытых позиций, не заточен под
  конкретную биржу). Причина — через `GET /v5/algo/order/history`
  (`state="effective"` + `actual_price`, прямой сигнал, как у Bybit/
  Aster/dYdX; параметр `type` у этого эндпоинта обязателен, поэтому два
  отдельных запроса, `type="sl"` и `type="tp"`). Цена закрытия (AE) —
  `GET /v5/trade/order/details` (`side`/`trade_price`/`trade_volume`
  прямо в ответе). Офиц. страница документации `algo/order/history`
  указывает "Signature verification: No" — похоже на ту же неточность
  документации HTX, что уже встречалась с `mark_price` выше; запрос
  всё равно подписывается по общей v5-схеме. НЕ ПРОВЕРЕНО на реальном
  срабатывании SL/TP (нет доступа к аккаунту из этой среды разработки);
- **спот-нога** (`entry_price._search_spot_entry`/`_search_spot_exit`,
  используется `short_position_tracker.py`/`sltp_alerts.py`/веб-
  калькулятором) — `GET /v1/order/matchresults` ("Search Match
  Results"), ОТДЕЛЬНЫЙ спот-API HTX (хост `api.huobi.pro`, та же
  классическая схема подписи, что и у баланса выше — `funding_report.
  _htx_sign` с явным `host`). Символ — слитно и в нижнем регистре
  (`"btcusdt"`, не `"BTC-USDT"`, как у фьючерсов). Параметр `types`
  фильтрует направление и тип ордера сразу (`buy-market`/`buy-limit`/...
  или `sell-*`) — официально задокументированный список значений, не
  угадывание. Максимальное окно запроса у эндпоинта — 48 часов (сдвигаемое
  в пределах 120 дней) — не ограничение этого кода, а лимит самого API;
  окна поиска в `entry_price.py` (20 мин/6 часов) в разы меньше, так что
  на практике не задевается. `_htx_spot_account_id`/`_htx_spot_signed_get`
  в `entry_price.py` НЕ импортируются из идентичных функций в
  `balances.py` — `balances.py` сам импортирует `entry_price.
  _etherscan_get`, обратный импорт создал бы циклическую зависимость
  между модулями, поэтому здесь небольшое намеренное дублирование.

Важная деталь для первых трёх пунктов: `volume` у HTX — в КОНТРАКТАХ, не в
монетах (тот же случай, что у MEXC `holdVol`) — домножается на
`contract_size` с публичного `GET /linear-swap-api/v1/swap_contract_info`
(`entry_price._fetch_htx_contract_size`, кэшируется в памяти процесса;
этот эндпоинт не затронут миграцией, см. выше).

На этом исходный план интеграции HTX (роль "Оба" — шорт на фьюче + лонг
на споте) реализован полностью, тем же пошаговым способом, что и у dYdX —
см. раздел выше.

## Алерты о закрытии позиции

Раз в `SLTP_CHECK_INTERVAL_MINUTES` минут (по умолчанию 2) бот сверяет
список сейчас открытых позиций с тем, что было на предыдущей проверке
(включая KuCoin, с момента как он добавлен в `funding_alerts.
get_open_positions()` — см. «KuCoin в funding-контуре» выше). Если позиция
пропала из списка — она закрылась, и алерт в Telegram уходит **на любой из
шести бирж, независимо от причины** (вручную, по стоп-лоссу, по
тейк-профиту, по ликвидации) — сам факт закрытия определяется одинаково
надёжно везде, тут не нужно лезть в историю ордеров конкретной биржи.

Дополнительно, где это можно определить надёжно, бот уточняет саму причину
и помечает её в тексте алерта (🛑 стоп-лосс / 🎯 тейк-профит, с ценой
закрытия) — сейчас это **Bybit и Aster**, у обеих бирж исполненный ордер
явно помечен полем, однозначно указывающим на SL/TP (`stopOrderType` у
Bybit, `origType` у Aster). Для MEXC/Gate/Lighter/KuCoin такого же надёжного
публичного сигнала не нашлось — алерт всё равно уходит (⚪️ Позиция
закрыта), просто без уточнения причины (см. докстринг `sltp_alerts.py`).

При каждом обнаруженном закрытии (на любой из шести бирж) бот также
записывает в соответствующую строку Google Sheet (та же таблица и то же
сопоставление монета+биржа → строка, что и в столбце P, см.
`sheets_sync.record_position_close`):

- **F** — дата закрытия: копирует туда текущее значение ячейки **F6**
  (снимок времени, как при ручном закрытии сделки), а не формулу и не
  время выполнения скрипта;
- **AE** — СРЕДНЕВЗВЕШЕННАЯ (VWAP) цена закрытия ФЬЮЧЕРСА по всем
  исполнениям в окне `CLOSE_PRICE_LOOKBACK_MINUTES` (по умолчанию 6 часов),
  а не последнее исполнение — пользователь закрывает позиции и частями, а
  не всегда одним ордером. Поддерживается для **Bybit/Aster/MEXC/Gate**
  (`GET /v5/execution/list`, `/fapi/v1/allOrders`,
  `/api/v1/private/order/list/order_deals/v3`, `/api/v4/futures/{settle}/
  my_trades` соответственно — эндпоинты для MEXC/Gate подтверждены по
  офиц. SDK ccxt) — для **Lighter и KuCoin** надёжного публичного эндпоинта
  истории сделок не нашлось (та же ситуация, что и с уточнением причины
  SL/TP ниже), AE остаётся пустой. На Bybit/Aster в усреднение попадают только
  исполнения СО СТОРОНОЙ ЗАКРЫТИЯ (там есть явное надёжное поле "side") —
  на MEXC/Gate такого поля нет (у MEXC сторона — необъяснённый в
  документации числовой код, у Gate явного поля стороны в сделке вообще
  нет), поэтому для них окно короче (`SLTP_LOOKBACK_MINUTES`, не
  `CLOSE_PRICE_LOOKBACK_MINUTES`) — минимизирует (но не исключает
  полностью) риск случайно усреднить в том числе сделку открытия позиции;
- **AD** — СРЕДНЕВЗВЕШЕННАЯ цена закрытия на СПОТЕ: бот ищет ВСЕ продажи
  того же актива в окне `CLOSE_PRICE_LOOKBACK_MINUTES` по всем подключённым
  спот-биржам сразу (Bybit/MEXC/Gate/KuCoin) — симметрично тому, как при
  открытии позиции ищется покупка (см. `entry_price._search_spot_exit`,
  зеркало `_search_spot_entry`), сторона сделки (buy/sell) здесь везде явно
  задокументированное поле, так что окно можно не сокращать. Uniswap в
  этом поиске не участвует — сканер кошелька умеет находить только
  входящие переводы (покупки), не исходящие (продажи).

Каждая из трёх записей — независимая попытка: если что-то одно не
нашлось/не удалось определить (например, нет цены закрытия фьючерса на
Lighter, или продажа на споте не нашлась в окне) — это не мешает записать
остальное. Если строка в таблице не находится однозначно (0 или несколько
совпадений) — вся запись пропускается, как и в остальных местах, где бот
пишет в эту таблицу. После записи бот читает каждую ячейку ОБРАТНО и
сверяет с тем, что писал, — если Google Sheets API отчитался об успехе, но
фактически ничего не применил (реальный случай 12.09.2026), это будет
видно в логах как отдельная ошибка, а не молчаливое "записано".

**Важно (реальный баг, найденный на живом аккаунте 31.08.2026):** временный
сетевой/API-сбой при запросе списка открытых позиций на КОНКРЕТНОЙ бирже
раньше выглядел для бота точно так же, как "открытых позиций на этой бирже
больше нет" — единичный сбой на, например, MEXC заставлял бота решить, что
ВСЕ открытые на MEXC позиции только что закрылись разом: ложный алерт в
Telegram ("Позиция MEXC BTW_USDT закрыта") и ложная запись даты закрытия в
столбец F для связки, которая на самом деле оставалась открытой.
Исправлено: `funding_alerts.get_open_positions()` теперь возвращает ещё и
множество бирж, у которых запрос в этом проходе завершился ошибкой — для
них `sltp_alerts.py` (и алерты по ставке funding в `funding_alerts.py`)
просто пропускают сравнение в этом проходе вместо того, чтобы принять
отсутствие данных за отсутствие позиций.

## Синхронизация с Google Sheet (столбец P)

`sheets_sync.py` раз в `SHEET_SYNC_INTERVAL_MINUTES` минут (по умолчанию
60) автоматически заполняет столбец **P** ("Прибыль" по "Бирже 2") в
таблице учёта сделок — туда, куда раньше суммарный funding по открытым
позициям вписывался вручную.

Как это работает:

1. Строка таблицы считается кандидатом на автозаполнение, если её статус
   (столбец **C**) — `active` (открыта: заполнена дата открытия **D**,
   дата закрытия **F** пуста). Для строк со статусом `done` P не трогается
   — там уже финальное значение сделки.
2. Из столбца **O** ("Биржа 2") берётся название биржи. Автоматически
   заполняются только строки, где эта биржа — одна из шести, для которых
   этот скрипт умеет считать funding (Aster/Bybit/Lighter/MEXC/Gate/
   KuCoin). Строки с другими биржами (paradex, edgex, apex, hyper и т.п.)
   скрипт пропускает не трогая — API-доступа к ним у бота нет вовсе.
3. Из столбца **B** (название монеты, например `"ZRO( (spot/perp)"`)
   извлекается базовый актив — текст до первой открывающей скобки
   (`"ZRO"`). Он сопоставляется с открытыми СЕЙЧАС позициями на нужной
   бирже (тем же кодом извлечения базового актива, что и в автоподборе
   цен калькулятора).
4. Если совпадение однозначное — записывается суммарный funding с момента
   открытия текущей позиции (та же логика, что и в команде `/positions`
   Telegram-бота: для Bybit/MEXC — точно от времени открытия, для
   Aster/Lighter/Gate — по непрерывности начислений). Если совпадений 0
   или больше 1 — ячейка не трогается, а в лог печатается причина.

Пишутся только сами ячейки `P{row}` для подошедших строк — остальные
ячейки, формулы и форматирование таблицы не затрагиваются.

### Первоначальная настройка (один раз)

1. В [Google Cloud Console](https://console.cloud.google.com/) включить
   Google Sheets API, создать Service Account, скачать его JSON-ключ.
2. Открыть свою Google-таблицу → «Настройки доступа» → добавить email из
   поля `client_email` внутри скачанного JSON как **редактора**.
3. На Railway добавить переменные окружения `GOOGLE_SHEET_ID` (id из URL
   таблицы) и `GOOGLE_SERVICE_ACCOUNT_JSON` (содержимое JSON-ключа
   целиком) и передеплоить — поток синхронизации запустится сам.

Если таблица содержит несколько вкладок и нужная — не первая, задать её
имя явно через `GOOGLE_SHEET_TAB`.

## Отслеживание новых шорт-позиций (столбцы B/D/M/O/W/X/Y)

`short_position_tracker.py` раз в `SHORT_POSITION_CHECK_INTERVAL_MINUTES`
минут (по умолчанию 60, независимо от `SHEET_SYNC_INTERVAL_MINUTES` выше)
проверяет все 7 подключённых бирж (Aster/Bybit/KuCoin/Lighter/MEXC/Gate/
dYdX) на новые открытые шорт-позиции и, если находит для позиции
встречную покупку той же монеты на споте на тот же объём, сам создаёт
новую строку в таблице — автоматизирует ручной ввод, который иначе
пользователь делает сам в момент открытия сделки. dYdX добавлен позже
остальных (реальный случай: позиция по SEI — спот MEXC, шорт dYdX — не
попала в таблицу автоматически именно потому, что dYdX на тот момент не
был подключён вообще; см. раздел «dYdX v4» выше про то, что из этого
файла для dYdX уже работает).

Как это работает:

1. Для каждой настроенной биржи запрашиваются ВСЕ текущие открытые
   позиции и из них отбираются именно ШОРТЫ (по знаку объёма/полю side —
   у каждой биржи своё, см. докстринг модуля; для Lighter конвенция не
   подтверждена официально, см. предупреждение ниже).
2. Для каждой найденной шорт-позиции проверяется, нет ли уже АКТИВНОЙ
   строки в таблице с той же парой (биржа в O, монета в B) — если есть,
   сделка уже записана, ничего не делается. Отдельного состояния между
   запусками бот не хранит (переживёт рестарт Railway без дублей и без
   пропусков) — сама таблица и есть источник истины о том, что уже
   записано.
3. Если активной строки ещё нет — ищется покупка той же монеты на споте
   (на любой из подключённых спот-бирж, а если задан
   `UNISWAP_WALLET_ADDRESS` — ещё и там) рядом по времени с открытием
   шорта. Переиспользуется та же функция поиска, что и в автоподборе цены
   калькулятора (`entry_price._search_spot_entry`) — те же окна поиска:
   ±20 минут, если биржа отдаёт точное время открытия (Bybit/MEXC/KuCoin),
   ±6 часов, если точного времени нет и оно оценивается по непрерывности
   funding (Aster/Gate/Lighter, тот же приём, что и в остальном боте).
4. Если покупка нашлась, но объём отличается от объёма шорта больше чем
   на **±1%** — строка не создаётся (мог случайно совпасть по времени
   несвязанный ордер). Если покупка не нашлась вовсе на всех спот-биржах
   в окне поиска — тоже не создаётся. В обоих случаях причина печатается в
   лог Railway.
5. Если и биржа, и объём совпали — создаётся новая строка (первая
   свободная после последней РЕАЛЬНО заполненной, см. предупреждение про
   строку #200 ниже): **B** = `"МОНЕТА(spot/perp)"`, **D** = дата и время
   открытия шорта, **O** = биржа, и дополнительно:
   - **M** — название спот-биржи(-бирж), где нашлась встречная покупка, в
     формате `"Биржа spot"` (например, `"MEXC spot"`) — `spot_result
     ["exchanges"]` из `_search_spot_entry` уже содержит список всех бирж,
     чьи сделки вошли в VWAP по X; если их несколько — через запятую;
   - **W** — объём, купленный на споте (сумма по всем найденным спот-сделкам,
     если покупка была не одним ордером);
   - **X** — средняя цена покупки на споте (VWAP по тем же сделкам —
     `_search_spot_entry` считает её уже взвешенной, отдельно взвешивать
     не нужно);
   - **Y** — средняя цена входа шорта на фьючерсе (поле ответа биржи —
     `avgPrice`/`entryPrice`/`entry_price`/`openAvgPrice`/`avgEntryPrice` в
     зависимости от биржи, те же поля, что уже проверены и используются
     для автоподбора цены в калькуляторе, entry_price.py).

   Если для W/X всё нашлось (иначе строка не создаётся, см. пункт 4 выше),
   а вот Y (цена фьючерса) от биржи не пришла — ячейка Y остаётся пустой
   для ручного заполнения, а не заполняется нулём. Остальные ячейки строки
   (комиссии и т.п.) по-прежнему заполняет сам пользователь.

**Важные допущения, требующие проверки на реальном аккаунте:**

- **Часовой пояс столбца D — МСК.** Время открытия форматируется как МСК
  (`UTC+3`, та же зона, что и весь остальной бот) и пишется строкой вида
  `"ГГГГ-ММ-ДД ЧЧ:ММ:СС"` с `value_input_option=USER_ENTERED` — Google
  Sheets сам распознаёт такой формат как дату независимо от локали
  таблицы. Если часовой пояс самой Google-таблицы (Файл → Настройки
  таблицы) — НЕ МСК, отображаемое время будет отличаться от реального на
  разницу поясов (сам текст, который увидит Sheets при парсинге, не
  изменится, а вот что он ОЗНАЧАЕТ для таблицы — зависит от её пояса).
- **Сторона позиции у Lighter не подтверждена официально.** Поле `sign` в
  офиц. SDK (`elliottech/lighter-python`) описано только как `int`, без
  документированных значений — используется по аналогии со всеми
  остальными биржами (отрицательное = шорт), но это предположение. Если
  на Lighter появится строка для позиции, которая на самом деле лонг (или
  не появится для реального шорта) — это первое место для проверки.
- **Допуск объёма ±1%** и **автозапись только столбцов B/D/M/O/W/X/Y** (не
  P — см. предупреждение про KuCoin выше) — согласованы с пользователем
  явно при реализации, не угаданы.
- **Номер новой строки** — не `_FIRST_DATA_ROW + len(rows)` (было так до
  фикса, реальный случай: строка уехала на #200 вместо места сразу после
  последней настоящей сделки #107). Открытый диапазон `B{FIRST}:O`
  Sheets API отдаёт КАК ЗНАЧЕНИЯ ячеек, а не только "реально введённые
  пользователем данные" — если формула статуса (или любая другая) в
  столбце между B и O протянута заранее на много строк вперёд и
  возвращает `""` для ещё не используемых строк, эта `""` всё равно
  считается значением и раздувает подсчёт длины. Теперь следующая строка
  ищется по последней строке с непустой колонкой **B** (монета) — тот же
  признак "это настоящая строка", что уже используется везде в проекте.
- Схемы подписи запросов, которые эта проверка использует для всех 6
  бирж, переиспользуют уже существующие функции из `funding_report.py`/
